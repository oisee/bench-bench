Bench Bench · coding agents on real tasks · October 12–13, 2026

Which coding agents actually finish the job

15 model + harness combinations worked on 6 tasks taken from real repositories: three difficulty levels, hidden tests, no human help. Key findings come first, then the data behind them, then what you should not trust yet.

TL;DR

    00

    The six tasks

    Each task is a real merged pull request from one of three public repositories by the same author. The agent gets the repository at the parent commit plus a written brief, never the PR itself. Grading overlays the PR's own tests (hidden from the agent) onto the agent's working tree: acceptance tests must go from failing to passing, regression tests must keep passing. The levels climb from ordinary languages toward exotic targets: L1 is plain JS/Go, L2 generates ABAP, L3 is compiler work (a TypeScript→ABAP frontend and a Z80 language).

    How the runs were actually paid

    The cost columns above are not what this benchmark cost. They answer a different question: what the same tokens would cost if you paid the public API per token, which is what matters if you run agents in CI or at scale. In reality almost every run used a flat-rate coding subscription. A run on a subscription costs nothing extra until you hit the plan's rolling limit; then you wait for the reset (Opus hit Anthropic's weekly limit once and two launches had to be repeated).

    Three effects visible already

    05

    The two-critic protocol: a Luna pilot

    Builder → critic → fix → critic → fix. We took three Luna runs and repeated them under the new protocol. No extra tasks were solved, and time went up 2–10×. The critics did find real bugs, but the builder could not fix them.

    single passwith two critics
    05b

    Round 3: more effort or executable checks

    Four single runs on the two hardest tasks, prompted by Naresh Jain's article on behavioural harnesses. Visible checks: the odd-numbered cases of the held-out tests sit in the repository from the start as runnable examples. Final gate: after a normal session the same kind of examples run once, and only on failure the agent gets one repair session with the output. Grading is unchanged: the full held-out tests.

    • Sol on L3b. At high effort it solved the task in 13 minutes. A second medium run with the final gate also solved it, but its gate passed on the first check, so it never received feedback: it was effectively a second medium attempt that succeeded where the first one failed after 8 minutes. For Sol at medium, L3b is a coin flip; one run per cell cannot say more.
    • Luna on L2b. High effort with visible checks solved the task in 9 minutes for about $0.08; without them high failed. Medium with visible checks stopped after 3 minutes without passing even the visible examples. Checks help a model that keeps working on them; at medium effort Luna quits before using them.
    • Grader fix on L3b. The gate run first failed only because the agent added its own test named like the held-out one, so the package did not compile. As with L2a, the held-out function is now renamed during grading; all 8 L3b runs were regraded and only this one changed status (data/l3b-hidden-name-fix-audit.json).
    06

    Critic screening: who finds the bug without seeing the tests

    Each critic gets a finished patch, the brief and the full repository, but not the hidden-test results. It has to decide on its own whether the patch is correct. Screening is complete.

    Interim conclusion. Sol is the only critic that actively tries to break the patch. It caught every failure and found two real bugs in test-passing patches, both confirmed against the reference. The price is one false alarm and a habit of rejecting nearly everything. Opus is more careful: no false alarms, but it missed Sol's L3b failure, as did Fable, Qwen and both GLM critics. GLM approves almost everything: it caught 1 of 3 failures in Claude Code and 2 of 3 in Pi (one of them its own model's patch), and spends 16–30 minutes per review in either harness.

    Rejecting a test-passing patch is not necessarily a critic error

    Sol rejected Opus's L2b patch even though it passed the hidden tests, and attached an input that reproduces the bug. Running that input on the patch and on the upstream reference solution:

    input   "IF a = 1. x = f(\n p = 2 ).\nENDIF.\n"
Opus    "IF a = 1. x = f(\np = 2 ).\nENDIF.\n"     ← continuation lost its indent
ref     "IF a = 1. x = f(\n  p = 2 ).\nENDIF.\n"   ← two spaces

    The brief explicitly requires continuation lines to keep their indent, so this is a real bug the hidden tests do not cover. All three of Sol's rejections among the six screening patches were checked this way. Two were confirmed: the second bug is that Opus's L3b patch fails on a function returning an empty object type, which the reference handles. The third was a false alarm: the reference panics on the same input as Sol's own L2b patch. Sol also reviewed a seventh patch outside this table, Luna xhigh on L2b, which passes the tests. That rejection was confirmed too: 2 of its 4 findings reproduce only on the patch (a * 3. continuation turned into a comment, and GET BADI treated as a report event); the other 2 behave the same on the reference.

    07

    What not to trust yet

    1. One run per cell. A one-task difference between agents may be noise. There are no repeats anywhere yet.
    2. The old composite leaderboard score is biased. The jury only graded L1 and never saw the Luna runs; a run without a jury grade got a flat 60 points. This page therefore counts only solved tasks and time.
    3. Costs are list-price estimates. For models other than Opus and GLM-5.3, prices come from third-party trackers that sometimes disagree by up to 2×. Token counts are reported by each harness and are comparable only roughly: harnesses differ in how they cache and what they count as input.
    4. Hidden tests are incomplete. Critic screening found three test-passing patches (Opus on L2b and L3b, Luna xhigh on L2b) that diverge from the reference (section 06). Their "solved" status is overstated.
    5. L2a grader fix. A hidden test clashed by name with tests the agents wrote. After the fix, 4 failures became passes and L2 went to 18/30. Under the selection rule, Luna xhigh rather than GLM-5.3/Pi should then have reached L3. Luna xhigh was run on L3 afterwards (October 13): it solved L3a and failed L3b; the original GLM-5.3/Pi L3 runs stay in the data.
    6. All tasks come from one ecosystem (Go/TS tooling around ABAP). Whether the findings transfer to other projects is untested.
